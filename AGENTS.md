# Quizly — Nuxt 3 Quiz App

Real-time, code-based quiz app (Kahoot-style). Admins create quizzes; players join with a
4-char code, answer timed questions, and appear on a live leaderboard. UI strings are in
Indonesian.

## Commands

| Command | Description |
|---------|-------------|
| `npm run dev` | Dev server on `localhost:3000` |
| `npm run build` | Production build (also used by Netlify) |
| `npm run generate` | Static generation |
| `npm run preview` | Preview production build locally |
| `npm test` | Run unit tests once (Vitest, `server/**/*.test.ts`) |
| `npm run postinstall` | Runs `nuxt prepare` after install (auto) |

No lint or dedicated typecheck script. `vue-tsc` is installed but not wired to a script.

## Architecture

- **Framework**: Nuxt 3 + TypeScript + Tailwind CSS
- **Database**: Supabase PostgreSQL — schema in `supabase-schema.sql`, RLS lockdown in `supabase-rls-lockdown.sql`
- **UI**: shadcn-vue (`new-york` style) in `~/components/ui/`, auto-prefixed as `Ui*` (configured in `nuxt.config.ts`)
- **Styling utility**: `cn()` in `~/lib/utils.ts` (wraps `clsx` + `tailwind-merge`)
- **Auth**: Custom admin auth via HMAC-signed session tokens (see Auth section) — **not** Supabase Auth
- **Realtime**: Supabase Realtime publication on `quizzes` + `participants` tables for live leaderboard
- **Deployment**: Netlify (`netlify.toml`), Node 20, builds with `npm run build`, publishes `.output/server`
- **Testing**: Vitest (`node` environment), tests colocated under `server/` as `*.test.ts`

## Auth Model

- Login/register (`/api/auth/*`) verify credentials, then issue a signed token via `signSession()`.
- Token format: `base64url(payload).hmacSHA256(payload)` signed with `runtimeConfig.authSecret` (`AUTH_SECRET` env). TTL 7 days. Implemented in `server/utils/session.ts`.
- Client stores `adminToken`, `adminId`, `adminUsername` in `localStorage` after auth.
- Admin API calls send `Authorization: Bearer <adminToken>`; `requireAdmin(event)` (`server/utils/requireAdmin.ts`) verifies the token and returns the session (`{ sub, username, ... }`).
- Route middleware `admin-auth` (client-only) redirects to `/admin/login` when `adminToken` is missing — it does **not** validate the token; real enforcement is server-side per request.
- Password hashing: `salt:sha256_hash` (`sha256(password + salt)`), stored in `admins.password_hash`.

## Key Conventions

- Custom components use the `Ui` prefix — e.g. `<UiButton>`, `<UiInput>`, `<UiDialog>`, `<UiLabel>`, `<UiCard>`, `<UiTable>`, `<UiAlertDialog>`
- Admin routes guard with `middleware: 'admin-auth'`
- All privileged DB access goes through server API routes using `serverSupabaseServiceRole` (bypasses RLS); the anon client (`serverSupabaseClient`) is only used for non-sensitive reads
- Quiz ownership: every admin write checks `quizzes.admin_id === session.sub` before mutating
- Quiz codes are 4-character alphanumeric (auto-generated by DB function `generate_quiz_code()`); custom codes are uppercased and truncated to 4 chars server-side
- Scoring: `1000 + (time_left * 10)` per correct answer, validated server-side at `/api/check-answer`

## Server API Routes

Auth & play (public):

| Route | Purpose |
|-------|---------|
| `POST /api/auth/register` | Create admin (username ≥3, password ≥6), returns token |
| `POST /api/auth/login` | Login admin (SHA-256 with salt), returns token |
| `POST /api/check-answer` | Server-side answer validation & scoring |
| `POST /api/play/join` | Resolve a quiz code to a quiz id |
| `GET /api/play/[id]/questions` | Fetch questions/options for playing |
| `POST /api/play/[id]/finish` | Save participant score |
| `GET /api/play/[id]/result` | Fetch a player's result |

Admin (require `Authorization: Bearer` via `requireAdmin`):

| Route | Purpose |
|-------|---------|
| `GET /api/admin/quizzes` | List the admin's quizzes |
| `POST /api/admin/quizzes` | Create a quiz |
| `GET /api/admin/quizzes/[id]` | Get one owned quiz |
| `PATCH /api/admin/quizzes/[id]` | Update an owned quiz |
| `DELETE /api/admin/quizzes/[id]` | Delete an owned quiz |
| `GET /api/admin/quizzes/[id]/participants` | List participants |
| `POST /api/admin/quizzes/[id]/questions` | Add a question + options (ownership-checked) |
| `DELETE /api/admin/questions/[id]` | Delete a question |

## Pages

- `/` — landing + join-by-code (`pages/index.vue`)
- `/admin/login` — login/register toggle
- `/admin` — admin dashboard
- `/admin/quiz/[id]` — quiz editor
- `/quiz/[id]` — play
- `/quiz/[id]/result` — player result/leaderboard

## Database (Supabase)

Tables: `quizzes`, `questions`, `options`, `participants`, `admins`
- RLS **locked down**: anon role has no access to `quizzes`/`questions`/`options`/`admins`; `participants` is anon-readable only (for the public realtime leaderboard). All writes go through service-role server routes.
- `quizzes.admin_id` references `admins(id)` (cascade delete) and scopes ownership
- `quizzes.code` is unique, auto-generated via `generate_quiz_code()` in SQL
- `quizzes.is_leaderboard_visible` toggles leaderboard display
- Password hashing: `salt:sha256_hash` format in `admins.password_hash`
- `questions.time_limit` defaults to 30s; admin configures 2–6 options per question

> Note: `supabase-schema.sql` currently declares the `admins` table twice. `admins` must exist before `quizzes` (FK dependency); apply the first definition and skip the duplicate.

## Environment

`.env` (copy from `.env.example`):

- `SUPABASE_URL`, `SUPABASE_KEY` (anon), `SUPABASE_SERVICE_KEY` (service role)
- `AUTH_SECRET` — long random string (min 32 chars) used to sign session tokens

## Setup

1. Copy `.env.example` → `.env` and fill in Supabase credentials + `AUTH_SECRET`
2. Run `npm install` (triggers `nuxt prepare` via postinstall)
3. Run `supabase-schema.sql` in your Supabase SQL editor (then `supabase-rls-lockdown.sql` if migrating from older wide-open policies)
4. `npm run dev`
